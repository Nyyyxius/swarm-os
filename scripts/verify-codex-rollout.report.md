Notes: **`/compact`: same rollout file, no new file, counters do NOT reset.** The compaction is written *into the running rollout*, and `total_token_usage` keeps climbing straight through it (it is cumulative billing and knows nothing about compaction). Honest limit of this run: the session was deliberately tiny (~11.6 K tokens, i.e. the fixed preamble floor and essentially nothing else), so there was nothing for the compaction to shrink — `last_token_usage.input_tokens` went 11606 → 11621, a non-event. **The expected post-compaction drop in `last_token_usage.input_tokens` was therefore NOT observed here, and this spike does not prove it.** It follows from the semantics (`/compact` replaces history with a summary, and the next request re-sends that smaller history), but a tracker that wants to *detect* compaction should be validated on a genuinely loaded session before relying on the drop. **`/new`: NEW FILE (+1), counters restart from scratch** (cumulative fell 34890 → 11660). codex allocates a fresh thread (new `thread-id` in `notify`, verify-codex C5) and with it a new rollout in the same `sessions/YYYY/MM/DD/` tree; the previous file stops growing. **Sharp edge — the new file is created lazily.** Its filename is stamped with the thread's creation time (the moment `/new` ran), but the file only *materialises on the new thread's first model request*: in this run the phase mark right after `/new` still saw a single file, and the second one appeared only during the following turn. So after a reset there is a window — however long the agent stays idle — during which "most recent rollout" still resolves to the **stale** previous file, which is complete and plausible-looking. A tracker must therefore either key on the `thread-id` from `notify` (which changes at the reset, immediately) or treat readings as stale until a file whose name carries the new thread-id exists. Consequence: **re-resolve the path after every reset**; never latch onto the file found at boot. swarm-os maps its `ContextResetCommand` `/clear` onto codex's `/new` (codex.ts:717-719), so this is the normal path, not an edge case.

Notes: A per-session CODEX_HOME contains **2 rollout files** — one per codex *thread*, not one per CODEX_HOME. Every `/new` (and `/clear`) starts a new thread and therefore a new file. Prefer mtime — it also tracks *appends*, so it identifies the file currently being written even in the pathological case of two threads created in the same second. Belt-and-braces alternative when the tracker already knows the thread: `notify` hands over `thread-id`, which is exactly the uuid in the rollout filename — an exact-match lookup with no ordering heuristic at all.

## Recommandation d'implémentation — le tracker

**Verdict : faisable, sans aucune dépendance nouvelle.** Un poller de quelques dizaines de lignes suffit ; tout ce dont il a besoin est déjà écrit, en continu, dans le `CODEX_HOME` que `prepareSessionConfig` crée déjà par session.

### 1. Résolution du chemin

```ts
// $CODEX_HOME/sessions/YYYY/MM/DD/rollout-<ISO>-<thread-uuid>.jsonl
const dir = path.join(configDir, 'sessions');           // configDir = SessionConfigResult.configDir
// 1er choix : match exact sur le thread-id fourni par `notify` (aucune heuristique)
//   rollout-*-<threadId>.jsonl
// repli : le plus récent par mtime (walk récursif, filtre /^rollout-.*\.jsonl$/)
```

**Le fichier n'existe PAS au boot** (sonde boot-only, R1) : il naît à la première requête modèle. Le tracker doit tolérer l'absence et re-résoudre jusqu'au premier tour.

Il doit **re-résoudre après chaque reset** — `/new` ouvre un nouveau fichier (R5/R6). Piège : ce nouveau fichier est **créé paresseusement**, à la première requête du nouveau thread, alors que son nom porte l'horodatage du `/new`. Entre les deux, « le plus récent » désigne encore l'ancien fichier, complet et crédible. D'où la préférence pour le match exact sur `thread-id`, qui bascule, lui, immédiatement.

### 2. Lecture

Lecture incrémentale par offset d'octets (`tail -c +<offset>`), avec un buffer de ligne partielle. Le fichier est flushé en continu, y compris **pendant** un tour (R3). Poll à 1 s largement suffisant (le spike a poll à 200 ms ; le signal ne change qu'une fois par requête modèle).

### 3. Champ à lire

```ts
// ne garder que ceci, et ignorer tout le reste
if (evt.type === 'event_msg' && evt.payload?.type === 'token_count' && evt.payload.info) {
  const { last_token_usage: last, model_context_window: win } = evt.payload.info;
  // last_token_usage = comptabilité de la DERNIÈRE requête ; comme chaque requête
  // renvoie toute la conversation, last.input_tokens EST l'occupation courante.
  const used = (last.input_tokens ?? 0) + (last.output_tokens ?? 0);   // == last.total_tokens
  const pctUsed = win > 0 ? (used / win) * 100 : null;
}
```

**Formule retenue : `last_token_usage.total_tokens / model_context_window`.**

- `total_token_usage` est un **compteur cumulatif de facturation**, pas une occupation : sur un rollout réel de cette machine il atteint **11 724 290** pour une fenêtre de **258 400** (45×). L'utiliser donnerait un « contexte utilisé » de 4500 %. **À bannir pour ce calcul** (il reste utile pour un coût/consommation de session).
- `cached_input_tokens` est un **sous-ensemble de `input_tokens`** (cache prompt), pas un supplément : ne pas l'additionner, sous peine de double comptage.
- `model_context_window` (258400 pour `gpt-5.4-mini`) vient de l'événement lui-même. Ne pas le coder en dur : c'est la fenêtre **effective** de codex, déjà rabotée par rapport aux 272 000 annoncés dans `models_cache.json`.
- `info` est **nullable** : des `token_count` porteurs uniquement de `rate_limits` arrivent sans chiffres d'usage. Les ignorer (ne surtout pas lire 0).
- Garder **le dernier** événement, pas une somme : le même couple de chiffres peut être ré-émis à l'identique, et un tour peut produire plusieurs événements.

**Validation croisée** : `/status` affiche « Context window: 57% left (119K used / 258K) » et le nombre « used » qu'il montre est exactement `last_token_usage.total_tokens` du rollout. On lit donc la même chose que l'UI de codex.

**Écart assumé sur le pourcentage** : codex n'affiche pas le ratio brut. Il retranche un socle incompressible (prompt système + définitions d'outils), estimé ici à **~13 000 tokens** — d'où « 100% left » à 11626 tokens utilisés, et « 57% left » là où le ratio brut donnerait 54%. Pour swarm-os : **garder le ratio brut**, qui est l'occupation physique et donc le bon déclencheur de compaction. Ne reproduire le socle que si l'UI doit afficher le même chiffre que `/status` — et alors l'assumer comme une approximation calée sur deux mesures (R4), pas comme une constante connue.

### 4. Bonus déjà disponible

Le même événement transporte `rate_limits` : `primary.used_percent`, `window_minutes`, `resets_at` (epoch), `plan_type`, `credits`. C'est la consommation du quota du compte — gratuite à collecter puisqu'on lit déjà la ligne, et exactement ce qu'il faut pour anticiper un throttling de la flotte.

### 5. Détection de compaction — ce qui reste à vérifier

`/compact` n'ouvre pas de nouveau fichier et ne remet pas `total_token_usage` à zéro. Le signal attendu d'une compaction réussie est **la chute de `last_token_usage.input_tokens`** à la requête suivante. **Ce spike ne l'a pas observé** : la session de test était volontairement minuscule (~11,6 K tokens, soit le plancher et rien d'autre), donc la compaction n'avait rien à compacter (11606 → 11621). La sémantique le prédit, mais si le tracker doit *détecter* la compaction, valider ce point sur une session réellement chargée avant de s'y fier.

### 6. Ce que le tracker ne coûte pas

Aucune requête modèle, aucun appel réseau, aucun flag CLI supplémentaire, aucune modification de la config codex générée : le rollout est écrit de toute façon. Le tracker est un lecteur passif d'un fichier que swarm-os possède déjà (`configDir` de `prepareSessionConfig`), détruit avec la session.
